**What:** Each pipeline is a `forward_X(od) → (transformed, *aux)` / `inverse_X(transformed, *aux) → od` pair where `*aux` carries the small bit of state needed to invert.
**When to use:** All three pipelines — D-09.1-17 locks this.
**Example:**

```python

def forward_minmax_od(od: torch.Tensor) -> Tuple[torch.Tensor, torch.Tensor, torch.Tensor]:
    od_min, od_max = torch.min(od), torch.max(od)
    scaled = (od - od_min) / (od_max - od_min)  # [0, 1]
    return scaled, od_min, od_max

def inverse_minmax_od(
    scaled: torch.Tensor, od_min: torch.Tensor, od_max: torch.Tensor
) -> torch.Tensor:
    return scaled * (od_max - od_min) + od_min
```

### Anti-Patterns to Avoid

- **One giant notebook that loops over 15 (pipeline, seed) pairs.** If kernel dies on run 12, you lose runs 1–11. Notebooks cannot resume.
- **Re-implementing the training loop per pipeline.** D-09.1-16 forbids it. Use `train_wgan_gp` (`core/training.py:178`) with different preprocessed input only.
- **Calling `np.random.seed(seed)` globally** instead of `np.random.default_rng(seed)` per data path. D-09.1-18 forbids the former. NOTE: `core/training.py:211-215` already calls `np.random.seed(seed)` — this is acceptable because it's inside the controlled training loop, but new code must not introduce additional `np.random.seed` calls.
- **Plotting helpers inside `core/`.** D-09.1-19 forbids it. Plot code lives in notebooks.

## Common Pitfalls

### Pitfall 1: Pipeline B variance accumulates under cumulative integration

**What goes wrong:** Inverting log-returns by `OD_t = OD_0 · exp(Σ r_i)` accumulates noise variance with horizon length. Small per-step bias in the synthetic log-returns becomes large bias in the reconstructed OD trajectory at late time-steps. This is the well-known geometric-Brownian-motion accumulation effect `[CITED: arxiv:2507.19003 — "A diffusion-based generative model for financial time series via geometric Brownian motion"]`.
**Why it happens:** `exp(Σ r_i)` exponentially amplifies any drift in the sum.
**How to avoid:** (a) Anchor each window to a real OD₀ from the same window in the real data (CD-5 — see Question 3 below), and (b) work on length-10 windows (`WINDOW_LENGTH=10`), not on full 778-point trajectories, so the cumulative integration runs for at most 10 steps — short enough that drift accumulation is bounded.
**Warning signs:** Pipeline B's OD-scale ACF lag-1 looks fine but later lags drift dramatically; Pipeline B's late-window OD values diverge from the real OD range.

### Pitfall 2: Pipeline A min-max with global statistics clips synthetic samples

**What goes wrong:** Min-max to [0, 1] using global `(od_min, od_max)` from training data. If the generator produces outputs in [-1.1, 1.1] (the v1.1 generator output range is [-1, 1] via PauliX/PauliZ, scaled by 0.1 — see `training.py:283`), un-normalizing maps that into `od_min - 0.1·(od_max - od_min)` and `od_max + 0.1·(od_max - od_min)` — slight OD-range overshoot, not a clipping disaster.
**Why it happens:** The generator output range and the [0, 1] target range don't quite match.
**How to avoid:** Document that Pipeline A's training feeds the normalized [0,1] data **then rescaled to [-1, 1]** via the existing `rescale` helper (`data.py:161-168`) — mirror v1.1's `scaled_data = -1 + 2*(transformed - min)/(max - min)`. The generator then naturally produces [-1, 1] outputs. Inverse rescales [-1,1] → [0,1] → OD. This matches v1.1's pipeline shape exactly, just with a different transform in the middle.
**Warning signs:** Pipeline A samples cluster at the edges of OD range (clipping) or have unrealistic excursions (no clipping).

### Pitfall 3: ACF mean-band loses sample-level structure

**What goes wrong:** "Mean ACF across samples with ±1σ band" can hide bimodality — e.g., if half the synthetic samples have ACF≈0 and half have ACF≈0.5, the mean is 0.25 with a wide band that doesn't reflect actual sample behavior.
**Why it happens:** Pooling per-sample ACF curves into a Gaussian band assumes unimodality.
**How to avoid:** In addition to the mean ± 1σ band, overlay a few individual sample ACF curves (faint lines) — the existing v1.1 notebook does this at `qgan_pennylane.ipynb:7426` (2×3 subplot grid pattern with per-sample faint lines). Eyeball check: do individual lines cluster around the mean, or split into clusters?
**Warning signs:** Wide ±1σ band with sharp asymmetry; mean ACF doesn't pass through the bulk of individual lines.

### Pitfall 4: Per-seed runs sharing global numpy random state

**What goes wrong:** If `run_ablation.py` is parallelized via `multiprocessing.Pool`, all forked processes inherit the same numpy global random state `[CITED: joblib.readthedocs.io/en/latest/auto_examples/parallel_random_state.html]`, so seed-42 and seed-43 produce identical noise streams.
**Why it happens:** `os.fork()` copies the numpy state from the parent.
**How to avoid:** Run each (pipeline, seed) as a **separate Python process** invoked from a shell loop, not as workers in a multiprocessing pool. The OS gives each process a fresh interpreter, and `train_wgan_gp(seed=N)` correctly re-seeds at line 211-215. If parallelism is desired, use `xargs -P 2` or `GNU parallel` to dispatch processes, never `multiprocessing.Pool` for the training step.
**Warning signs:** Two seeds produce bit-identical loss curves and bit-identical generated samples.

### Pitfall 5: TSTR-lite over-fits to a single LSTM hyperparameter point

**What goes wrong:** A single LSTM choice (1 layer, 32 hidden units, learning rate X) could land anywhere on a U-curve of validation MSE — a different choice might rank pipelines A/B/C completely differently.
**Why it happens:** Small networks are sensitive to architecture; this is a known TimeGAN-evaluation concern `[CITED: github.com/jsyoon0823/TimeGAN — "Network parameters should be optimized for different datasets"]`.
**How to avoid:** This phase's TSTR is **lite** by design (D-09.1-10). Document that the LSTM is a sanity scaffolding, not a final TSTR. Phase 11 (EVAL-01..04) owns the comprehensive TSTR. Pick a single defensible architecture (Question 5 below), report its number transparently, and don't claim it's the "TSTR result."
**Warning signs:** Reviewers attack the LSTM choice. Counter: "this is a sanity check; Phase 11 EVAL-01 owns the full TSTR with architecture-tuned forecaster."

### Pitfall 6: Pipeline C deviates from v1.1 published EMD outside 1–2%

**What goes wrong:** Pipeline C is supposed to reproduce v1.1 within 1–2% (D-09.1-12). If it deviates more, the comparison is corrupted because Pipeline C is no longer "the v1.1 pipeline."
**Why it happens:** Phase 9 already verified parity = 0.0 at the metric level (`results/parity_check.json`, "delta": all zeros) so this shouldn't happen — but seed handling, eval batch size, or generated-sample count can introduce drift.
**How to avoid:** Pipeline C uses the *exact* same data preprocessing as `load_and_preprocess()` (`data.py:227-296`) and `train_wgan_gp(seed=42)`. The Phase 8 parity test already pins this to 0.0 deviation. Any non-zero deviation in Pipeline C's re-run signals a regression — the smoke test must verify this BEFORE the multi-seed launch.
**Warning signs:** Pipeline C's smoke-run EMD differs from `results/parity_check.json` `post.emd = 0.12048789...` by more than 1%.

## Code Examples

### Pipeline A — Min-Max Normalization (D-09.1-12 anchors to global per `dataset_stats.md`)

```python
# Source: pattern from core/data.py:161-168 (existing rescale helper)
def forward_minmax_od(
    od: torch.Tensor,
) -> Tuple[torch.Tensor, torch.Tensor, torch.Tensor]:
    """Min-max normalize OD to [0, 1] using GLOBAL extrema.

    Single-campaign data (docs/dataset_stats.md: 1 campaign, 778 rows)
    makes global min-max the natural choice — there is no inter-campaign drift
    to control for. Returns the (scaled, od_min, od_max) triple so the inverse
    can be exact.
    """
    od_min = torch.min(od)
    od_max = torch.max(od)
    scaled = (od - od_min) / (od_max - od_min)  # → [0, 1]
    return scaled, od_min, od_max


def inverse_minmax_od(
    scaled: torch.Tensor, od_min: torch.Tensor, od_max: torch.Tensor
) -> torch.Tensor:
    """Exact inverse of forward_minmax_od."""
    return scaled * (od_max - od_min) + od_min
```

### Pipeline B — Log-Returns with Cumulative Integration

```python
# Source: log-return forward pattern from core/data.py:48-64
def forward_logreturns(
    od: torch.Tensor,
) -> Tuple[torch.Tensor, torch.Tensor]:
    """Log-returns + standardization to zero-mean / unit-std.

    r_t = ln(OD_{t+1}/OD_t).  Returns (r_norm, (mu, sigma)).

    Notes:
      - Length contract: returns length N-1 (drops one timestep).
      - Single mu/sigma across the full series (global standardization),
        matching the v1.1 convention in core/data.py::normalize.
    """
    log_od = torch.log(od)
    r = log_od[1:] - log_od[:-1]
    mu = torch.mean(r)
    sigma = torch.std(r)  # default ddof=1 (matches v1.1 normalize() at data.py:36)
    return (r - mu) / sigma, mu, sigma


def inverse_logreturns(
    r_norm: torch.Tensor,
    od_start: torch.Tensor,  # shape (B,) — one OD₀ per window, real-data anchored
    mu: torch.Tensor,
    sigma: torch.Tensor,
) -> torch.Tensor:
    """Inverse: un-standardize, then cumulative-integrate from od_start.

    OD_t = OD_0 · exp(cumsum(r_1, …, r_t))

    Args
    ----
    r_norm
        Standardized log-returns. Shape (B, L-1) or (L-1,).
        L = window length (10 for v1.1).
    od_start
        Real-data OD₀ for each window (CD-5 decision — see RESEARCH.md Q3).
    mu, sigma
        Returned by forward_logreturns.

    Returns
    -------
    od : shape (B, L) — full OD trajectories anchored at od_start.
    """
    r = r_norm * sigma + mu                          # un-standardize
    # Cumulative sum along the time axis (last dim):
    cum = torch.cumsum(r, dim=-1)                     # (B, L-1)
    # Prepend zeros so OD_0 is preserved:
    pad = torch.zeros_like(cum[..., :1])              # (B, 1)
    cum_full = torch.cat([pad, cum], dim=-1)          # (B, L)
    # Reconstruct OD trajectory:
    log_od = torch.log(od_start).unsqueeze(-1) + cum_full
    return torch.exp(log_od)
```

### Round-trip gate (matches Phase 9 EVAL-06 pattern)

```python
# Source: 02_eval06_roundtrip.ipynb (verified-passing template)
def verify_roundtrip(pipeline_name: str, forward_fn, inverse_fn, od, *inv_extra_args) -> None:
    transformed, *aux = forward_fn(od)
    od_rt = inverse_fn(transformed, *aux, *inv_extra_args)
    err = (od_rt - od).abs().max().item()
    tol = 1e-8 if pipeline_name in {"A", "B"} else 1e-6  # C uses 1e-6 per D-09.1-03
    print(f"[{pipeline_name}] roundtrip max_abs_err = {err:.3e}  (tol ≤ {tol:.0e})")
    assert err <= tol, f"{pipeline_name} round-trip FAILED"
```

### Q3. Pipeline B cumulative-integration anchoring (CD-5)

**What we know:**
- Real data has windows of length 10 (stride 2) — 384 windows from 778 OD points.
- Each window has a known starting OD value from the real data.
- Three options: (a) real per-window OD₀, (b) sampled OD₀ from real-distribution, (c) fixed OD₀ (e.g., grand mean).

**What's unclear:**
- Does anchoring choice bias OD-scale ACF / Q-Q / PDF?

**Recommendation:** **Use real per-window OD₀ at inverse time.**
- For each generated synthetic log-return window (`B, 9`), pair it with a real OD₀ drawn from the real-data per-window starting-OD distribution. This matches the per-window evaluation protocol cleanly.
- For ACF specifically: ACF is **shift-invariant** when computed on a single trajectory — anchoring affects the absolute OD level, not the autocorrelation structure. So real-OD₀ vs sampled-OD₀ does NOT bias the ACF result. It only affects PDF/CDF and Q-Q if anchored values cluster differently from the real distribution `[VERIFIED: `numpy.correlate` definition — ACF removes the mean before computing covariance]`.
- For PDF/CDF / Q-Q on OD scale: real per-window OD₀ ensures the synthetic OD distribution starts from the same set of initial values, so any difference in the marginal distribution is attributable to the transformation's reconstruction error, not to a mismatched starting condition.

**Implementation:** In `run_ablation.py`, after generating N synthetic windows of log-returns, sample N starting-OD values from the real-window starting-OD set (with replacement). Document this choice in the `summary.md` Q2 paragraph: "Pipeline B inverse anchored at real per-window starting OD; ACF is shift-invariant so this choice does not bias the temporal-structure metric."

`[CITED: arxiv:2507.19003]` — GBM-based generative models for finance routinely anchor at the empirical starting price for the same reason.

### Q4. Pipeline A min-max — global vs per-trajectory

**What we know:**
- `dataset_stats.md` confirms a single campaign, single OD range, 778 rows.
- "Per-trajectory" min-max would require a notion of separate trajectories — but the data has one trajectory (the campaign), then sliced into 384 overlapping windows of length 10.
- The literature comparison `[CITED: arxiv:2512.02833 — "A Comparative Study on How Data Normalization Affects Zero-Shot Generalization in Time Series Foundation Models"]` shows MinMax under-performs Standardization/RevIN — but this concerns transfer-learning generalization, not a single-distribution ablation. Not directly applicable here.

**Recommendation:** **Global min-max from the full 778-point OD series.** Single-campaign means there is no inter-trajectory variation to control for; per-window min-max would destroy the relative-level information that the generator needs to learn (each window would be remapped to [0,1] losing its absolute height). Global preserves both shape and relative level.

**Sanity gate:** In the round-trip notebook, verify `inverse_minmax_od(forward_minmax_od(od)) == od` to within 1e-8 on the full 778-element OD tensor.

### Q5. LSTM forecaster for TSTR-lite (CD-4)

**What we know:**
- TimeGAN/Yoon et al. 2019 used GRU/LSTM with 24 hidden units for synthetic-data evaluation `[CITED: github.com/jsyoon0823/TimeGAN]`.
- D-09.1-10 specifies "small LSTM."
- TSTR-lite is **sanity scaffolding**, not the headline TSTR (Phase 11 EVAL-01 owns that).

**Recommendation:** **1-layer LSTM, 32 hidden units, sequence-length-9 → predict-1 horizon.**

```python
# Source: TimeGAN evaluation pattern (small forecaster for TSTR sanity)
class TSTRLiteLSTM(torch.nn.Module):
    def __init__(self, hidden=32):
        super().__init__()
        self.lstm = torch.nn.LSTM(input_size=1, hidden_size=hidden, num_layers=1, batch_first=True)
        self.fc = torch.nn.Linear(hidden, 1)
    def forward(self, x):  # x: (B, 9, 1) → y: (B, 1)
        out, _ = self.lstm(x)
        return self.fc(out[:, -1, :])
```

**Training protocol:**
- Input: window first 9 OD values; target: 10th OD value (next-step prediction within a v1.1 length-10 window).
- Train on synthetic OD trajectories from each pipeline (separate model per pipeline).
- Evaluate on **held-out real windows** — use the first 320 of 384 real windows for the held-out evaluation set (per-pipeline LSTM never sees these). Pipeline-specific train sets are the 10 × N_real ≈ 3840 synthetic windows × 5 seeds = up to 19200 synthetic windows.
- Loss: MSE; optimizer Adam at default LR `1e-3`; train for 50 epochs (cheap).
- Report MSE and R² on the held-out real set.
- For comparison: also train an LSTM on **real-only** (the non-held-out 64 real windows) and report its held-out MSE/R² as a baseline.

**Rationale:** 32 hidden units × 1 layer is the standard minimal LSTM forecaster `[CITED: machinelearningmastery.com/lstm-for-time-series-prediction-in-pytorch/]`. Single sequence-length-9 → 1-step prediction matches the v1.1 window structure. Reporting against a real-only baseline lets the reader gauge whether synthetic-data-trained models are competitive at all, without overclaiming.

**Caveat:** Document explicitly in `summary.md` that this is a sanity TSTR; Phase 11 EVAL-01 owns the full multi-architecture forecaster.

### Q6. Compute budget mitigation

**What we know:**
- 3 pipelines × 5 seeds × 1000 epochs ≈ 7.5× v1.1 single-seed (with 2000 epochs reduced to 1000).
- v1.1 single-seed wall time on local Mac: "hours" (PROJECT.md / dataset_stats.md context).
- PennyLane `default.qubit` does NOT meaningfully benefit from PennyLane-native parallelism on statevector simulators `[CITED: discuss.pennylane.ai/t/multiprocessing-for-simulator-devices/827]`.
- Parameter broadcasting (`qml.batch_input`, `batch_size` dim in QNode) IS used in v1.1 for per-batch generator calls — that's `B=12` per step, already batched (`training.py:282`). This is intra-step batching, not inter-seed batching.

**What's unclear:**
- Can we parallelize across seeds on a single Mac?

**Recommendation:**
- **Default to sequential execution.** Run one (pipeline, seed) at a time via the CLI. This is the safest, most reproducible default.
- **If the user wants parallelism:** Run **at most 2 processes in parallel** via `xargs -P 2` or GNU `parallel`. The Mac has limited memory bandwidth and the PyTorch + PennyLane stack is not multi-process-safe for shared state — separate processes are the only viable parallelization. Two parallel processes typically saturate a Mac's CPU; more risks thermal throttling on M-series Macs.
- **Checkpoint-resume strategy:** Each `run_ablation.py` invocation is idempotent — re-running `--pipeline A --seed 42` overwrites the previous artifacts cleanly. If a run dies partway, just re-invoke. No partial-resume needed; 1000 epochs at v1.1 batch size is hours, not days, per single run.
- **Critical: NEVER use `multiprocessing.Pool` from within a single Python process.** Forked workers share numpy global state and produce duplicate noise sequences `[CITED: joblib.readthedocs.io/en/latest/auto_examples/parallel_random_state.html]`. The shell-driven parallelism above avoids this entirely.

**Wall-time estimate (sequential):** Assuming v1.1 single-seed-2000-epoch ≈ 6 hours wall on a Mac → 1000-epoch ≈ 3 hours → 15 runs × 3h = **45 hours = ~2 days sequential**. With `xargs -P 2`, **~24 hours = ~1 day**. With +2 conditional seeds: add ~12 hours.

### Q9. Pipeline B numerical stability under cumulative integration

**What we know:**
- See Pitfall 1 above — short windows (length 10) bound the accumulation.
- The standardization step (`(r - mu) / sigma`) means generated samples are zero-mean / unit-std in transformed space; cumsum over 9 zero-mean steps is a Brownian-bridge-like trajectory with bounded variance.
- Variance of cumsum at lag t: `t · sigma²` (after un-standardizing). For t=9, sigma_log_return ≈ 0.022 (from Phase 8 parity output `_sigma_A=0.021759`), so cumsum-σ at horizon = `3 · 0.022 ≈ 0.066`, then `exp(0.066) ≈ 1.07` — OD changes by at most ±7% over a window. Bounded.

**Recommendation:** Pipeline B is numerically safe on length-10 windows. The cumulative-integration concern is real for full-trajectory reconstruction (777-step horizons) but NOT for per-window reconstruction (9-step horizons). Document this in `summary.md`: "Pipeline B inverse runs on 9-step windows; cumulative drift accumulates negligibly at this horizon."

`[CITED: arxiv:2507.19003]` — diffusion-based GBM models discuss horizon-dependent variance accumulation.

**Implementation note:** Use `torch.cumsum` (not a Python loop) for vectorized inverse — see the code example in "Code Examples → Pipeline B" above.
