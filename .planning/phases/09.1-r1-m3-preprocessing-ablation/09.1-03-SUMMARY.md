## Accomplishments

- **Resumable sweep driver** (`revision/run_ablation_sweep.sh`, committed in Task 2):
  - Loops over 3 pipelines × 5 seeds; encodes constants (PIPELINES, SEEDS={42,43,44,45,46}, EPOCHS=1000, STATUS_FILE).
  - `is_complete(p, s)` checks 5 artifact files exist AND are non-empty (`config.yaml`, `checkpoint.pt`, `samples.npy`, `metrics.json`, `inverse_kwargs.npz`).
  - `record_status` writes per-pair JSON to `sweep_status.json` via a Python heredoc using `os.rename` for atomicity (POSIX atomic rename — no flock race between xargs children).
  - CLI flags: `--parallel N` (default 1, hard-capped at 2 with helpful error), `--epochs M`, `--dry-run`.
  - Parallel mode (`--parallel 2`): builds a temp work-list of incomplete pairs, dispatches via `xargs -P 2 -L 1 bash -c '...'` so each pair runs in a fresh OS process (numpy/torch global state is per-process).
  - Sequential mode (default): nested for-loops, same is_complete + record_status pattern.
  - `set -euo pipefail` at top; failures of a single `python -m revision.run_ablation` invocation do NOT abort the sweep — they are recorded as `status: failed` so the user can investigate and re-invoke (sweep is idempotent: re-run skips complete pairs, retries failed pairs).

- **Full 3×5×1000-epoch matrix executed end-to-end**, monitored to completion:
  - All 75 artifact files (5 files × 15 runs) exist and are non-empty (verified via `os.path.getsize > 0` loop).
  - `sweep_status.json::all_complete` = `true`, `completed_count` = 15, `total_count` = 15.
  - Every `config.yaml` confirms D-09.1-04 invariants: `n_critic=9, lambda_gp=2.16, lr_critic=1.8046e-05, lr_generator=6.9173e-05, batch_size=12` (also `num_qubits=5, num_layers=4, window_length=10`) — checked across all 15 configs, 0 mismatches.

- **Wave-2 smoke artifacts preserved** under `revision/results/transform_ablation/_smoke_100ep_archive/{A,B,C}_42_100ep/` (5 files each, 15 total): when the sweep needed to write 1000-epoch outputs at the A/42, B/42, C/42 paths that wave 2 had occupied with 100-epoch outputs, the smoke artifacts were moved (not deleted) into an archive subdirectory. ## Decisions Made

1. **Smoke-archive instead of smoke-delete (recovery note).** Wave 2 produced 100-epoch runs at `runs/{A,B,C}/42/`. Wave 3 needed clean 1000-epoch outputs at the same paths. The `is_complete()` predicate validates file presence + non-emptiness only — it does NOT inspect epoch count. Letting the sweep skip those slots (because the 100-epoch artifacts satisfied `is_complete()`) would have silently mixed 100-epoch and 1000-epoch data into the wave-3 matrix. Two options: (a) `rm -rf runs/{A,B,C}/42/` then relaunch, (b) `mv runs/{A,B,C}/42 _smoke_100ep_archive/{A,B,C}_42_100ep/` then relaunch. Chose (b) — archive preserves the 100-epoch outputs for cross-checking against the 1000-epoch outputs (e.g., verifying that 1000-epoch outputs are NOT identical to 100-epoch outputs at the same seed, which would indicate the seed wasn't actually re-initialized). After the sweep, the 1000-epoch artifacts overwrote the (now-empty) A/42, B/42, C/42 slots cleanly.
2. **Conditional +2 seeds (D-09.1-06) deferred to plan 04.** The +2 seeds gate is analysis-time: it triggers only if inter-seed standard deviation in OD-scale metrics across the initial 5 seeds is too large to support a confident pipeline recommendation. That decision belongs to the plan-04 analysis notebook (after metrics.csv and ACF/PDF/Q-Q figures are computed), not to this sweep plan. The current 15-run matrix is the baseline; plan 04 may invoke the sweep again with `--parallel 2` and seeds {47, 48} appended to expand to 21 runs if needed. Re-invocation is idempotent: the 15 existing runs skip via `is_complete()`, only the new seeds train.
3. **--parallel 2 (xargs -P 2), not sequential.** RESEARCH Q6's `xargs -P 2` recommendation was followed. With actual per-pair wall ≈ 219 s and the run completing in 29.1 min at parallel=2, sequential would have taken ≈ 54.8 min — still well within a single working session. Parallel was used anyway to validate the parallel code-path under real conditions (it would have been awkward to discover a parallel-only bug in a future emergency rerun).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Smoke-output overwrite hazard — archived wave-2 100-epoch artifacts before launching 1000-epoch sweep**

- **Found during:** Task 3 pre-launch (after Task 2 commit, before `./revision/run_ablation_sweep.sh --parallel 2` invocation).
- **Issue:** Wave 2 (plan 09.1-02) committed 15 100-epoch artifact files under `runs/{A,B,C}/42/` for harness verification. Wave 3 needs 1000-epoch artifacts at the same paths. The sweep driver's `is_complete(p, s)` predicate checks only file presence and non-emptiness — NOT epoch count or any metadata that would distinguish a 100-epoch artifact from a 1000-epoch one. If the sweep had been launched without first clearing those paths, seeds A/42, B/42, C/42 would have been silently skipped, and the wave-3 matrix would have contained 3 × 100-epoch + 12 × 1000-epoch results — a subtle mixed-training-budget bug that would have polluted plan-04 analysis.
- **Fix:** Before invoking the sweep, ran `mkdir -p revision/results/transform_ablation/_smoke_100ep_archive && for p in A B C; do mv revision/results/transform_ablation/runs/${p}/42 revision/results/transform_ablation/_smoke_100ep_archive/${p}_42_100ep; done`. This preserved the 100-epoch artifacts for later cross-checking while clearing the A/42, B/42, C/42 paths so the sweep would train fresh 1000-epoch runs there. Chose archive over delete because the archived files cost ~2.3 MB per pipeline (~7 MB total) and forensic data is cheap.
- **Files affected:** Moved 15 files from `runs/{A,B,C}/42/` to `_smoke_100ep_archive/{A,B,C}_42_100ep/`. Sweep then wrote 15 new files into the cleared paths.
- **Verification:** After the sweep, the `runs/{A,B,C}/42/` paths contain the 1000-epoch artifacts (confirmed by metrics.json containing 1000-epoch loss curves, and by wall_seconds ≈ 218 s in sweep_status.json matching the 1000-epoch per-pair budget); the archived `_smoke_100ep_archive/{A,B,C}_42_100ep/` paths retain the original wave-2 100-epoch artifacts (confirmed by their file sizes matching the wave-2 commit).
- **Impact on D-09.1-04 invariant:** None — the archived smoke configs used the same HPO constants as the sweep (n_critic=9, λ=2.16, etc.); only the epoch count differed. D-09.1-04 is about training-condition equivalence across pipelines at a fixed budget, not about a fixed-budget across waves.
- **Committed in:** The archive lives in the same final plan-metadata commit as the SUMMARY (force-added under gitignored `results/`).

**2. [Rule 3 - Blocking] Sweep driver invoked system python; required project-venv python**

- **Found during:** First attempt to launch the sweep from `revision/run_ablation_sweep.sh` after the Task-2 commit (`92f70f7`).
- **Issue:** The initial sweep driver invoked `python -m revision.run_ablation ...` which resolved to the system python interpreter. The system python lacks the project's installed dependencies (PennyLane, torch, pyyaml). Every (pipeline, seed) invocation failed immediately at module-import time with `ModuleNotFoundError: No module named 'pennylane'`.
- **Fix:** Modified `revision/run_ablation_sweep.sh` to invoke the project venv's python explicitly (`./venv/bin/python -m revision.run_ablation ...` — or equivalent for the canonical project venv path). After this fix, all 15 pairs ran cleanly.
- **Files modified:** `revision/run_ablation_sweep.sh`.
- **Verification:** Post-fix relaunch produced 15/15 complete runs with return_code 0 across the board (verified in sweep_status.json).
- **Impact on D-09.1-04 invariant:** None — this was environment-hygiene plumbing, not a logic change. The training code, HPO constants, dataset paths, and seed handling were untouched.
- **Committed in:** `5d70586` (fix(09.1-03): use project venv python in sweep driver).
